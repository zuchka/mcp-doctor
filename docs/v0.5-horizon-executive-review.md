# Horizon deployment: executive review

Date: 2026-09-22  
Scope: MCP Doctor v0.5 authenticated beta  
Detailed evidence: [Horizon friction log](v0.5-horizon-friction-log.md)

## Executive summary

Horizon successfully delivered its central promise: it turned an MCP server in a GitHub
repository into a managed, authenticated internet endpoint without requiring us to assemble
our own cloud runtime, OAuth service, deployment pipeline, access gateway, audit system, and
rollback mechanism.

The resulting MCP Doctor beta is live, protected by mandatory authentication, and exposes
only one deliberately narrow diagnostic capability. We verified successful and denied
requests, privacy-preserving audit data, gateway rejection of unauthorized traffic, and a
complete rollback and restoration exercise.

The platform's core value proposition is therefore validated. The principal weakness was the
release workflow for a pull request that introduces a new server entrypoint. That path was
confusing and required workarounds that run counter to the normal safety practice of testing a
preview before merging it into the production branch.

Our overall assessment is **B+**: strong managed MCP infrastructure with an effective security
boundary, paired with deployment-onboarding and automation experiences that still feel
immature.

## What Horizon replaced

Without Horizon, a team could host the same Python process on a general cloud platform such as
DigitalOcean, Railway, AWS, or Google Cloud. The team would then need to select, integrate,
operate, and audit several additional systems:

- internet routing, TLS certificates, health checks, and scaling;
- OAuth-compatible user sign-in and token handling for MCP clients;
- server and tool access policies;
- Git-based builds, preview environments, promotion, and rollback;
- secrets management, operational logs, and usage visibility;
- an incident process joining identities, requests, code revisions, and outcomes.

Horizon supplied those shared platform responsibilities. MCP Doctor remained responsible for
the application-specific risks: deciding which remote servers may be inspected, preventing
server-side request forgery, refusing caller credentials, bounding time and data volume, and
returning safe results.

In simple terms, Horizon protected and operated the front door. MCP Doctor still had to ensure
that everything behind the front door behaved safely.

## What worked well

### The security boundary was real

Horizon required authentication before MCP discovery or invocation. Anonymous requests were
rejected, and a forged internet host was blocked by the gateway. MCP Doctor did not need to
receive, store, or validate the user's OAuth credentials itself.

This was the clearest platform benefit. It removed a difficult, security-sensitive subsystem
from the application while still allowing the application to enforce its own narrower policy.

### Production changes were controlled

New versions built without interrupting the live version. The production address remained
stable while Horizon built and health-checked replacements. Pull requests could receive
isolated preview targets once their configuration was recognized.

### Privacy controls were useful

Request and response payload storage could be disabled independently. Even with both disabled,
the traffic record still identified the caller, client, tool, deployment, outcome, duration,
and Horizon request. That is a sensible default for a diagnostic service that may encounter
sensitive system descriptions.

### Rollback worked

We promoted a previous image, waited for it to become live, and then restored v0.5. Both
transitions completed successfully, and the restored server again exposed exactly the intended
single tool. This converts rollback from a documented promise into tested incident capability.

### Least-privilege integration was possible

The Horizon GitHub application was granted access only to the MCP Doctor repository. The
hosted application required no OpenAI key, downstream bearer token, shared user credential, or
database secret.

## Findings by category

### Likely product defects

These behaviors appear inconsistent with a safe and predictable release workflow.

#### 1. A new pull-request entrypoint was validated against the production branch

The pull request introduced a new server entrypoint, but Horizon rejected that entrypoint
because the file did not yet exist on `main`. This meant the new server could not be tested in
its intended preview configuration before its source was merged.

Business impact: this creates pressure to merge code before the managed environment has tested
it. That weakens the value of preview environments precisely when a team is making a material
deployment change.

Recommended change: make the selected revision an explicit build input and validate its
entrypoint against that revision.

#### 2. Entrypoint validation could appear successful before it finished

The configuration briefly looked saveable, but the asynchronous validator had not completed
and earlier changes did not persist. We had to wait, move focus away from the field, save, and
reload the page to prove the setting was real.

Business impact: an operator can believe a production configuration changed when it did not.

Recommended change: show explicit `Validating`, `Valid`, `Saving`, and `Saved` states and retain
an auditable configuration revision.

#### 3. An existing pull request required close-and-reopen synchronization

A normal update to a pull request that predated the Horizon server did not register it for
preview deployment. Closing and reopening the same pull request generated the event Horizon
needed.

Business impact: the recovery mechanism is non-obvious, and closing a live review is a poor
operational signal.

Recommended change: automatically reconcile open pull requests when a server is connected, or
provide a visible `Register existing pull request` action.

### Product limitations or design gaps

These are not necessarily defects, but they should be documented or improved.

#### Build-time inspection does not receive encrypted runtime configuration

Horizon imports the MCP server during its image build to discover the tool manifest, but the
configured encrypted environment values were unavailable in that phase. A server that
correctly refuses to start without its runtime security policy can therefore fail its build.

We addressed this safely: the server can disclose its manifest in an unconfigured build state,
but every invocation fails before DNS resolution or network access until runtime policy is
present.

Recommended change: document the build/runtime boundary and provide a first-class manifest
inspection mode.

#### Preview governance is less visible than production governance

The Tool Permissions view reflects the live production manifest rather than the selected
preview. That behavior is understandable, but it makes preview verification less intuitive.

Recommended change: add a read-only effective-permissions view for each preview deployment.

#### Application correlation is lost when payload logging is disabled

Horizon preserved useful request metadata, but the application's own correlation identifier
was not available as an indexed field. Operators must correlate by time and Horizon request ID.

Recommended change: support safe custom indexed metadata independently of payload retention.

#### Plan-level capacity controls were unclear

The dashboard did not expose operator-configurable per-user rate limits, per-user concurrency,
or log retention for the account we used. MCP Doctor therefore relies on a global application
concurrency limit and keeps access restricted to authenticated organization members.

Recommended change: display fixed platform limits and retention beside the relevant settings,
and clearly distinguish plan-defined limits from operator-defined policy.

#### Scale-to-zero creates visible latency

The first preview connection took approximately 12 seconds. This is an expected economic
tradeoff rather than a defect, but it is long enough to affect interactive client behavior.

Recommended change: expose cold-start expectations and an optional minimum-warm setting where
plans support it.

### Issues outside Horizon

Several findings belonged to MCP Doctor or the wider MCP ecosystem rather than Horizon:

- MCP Doctor relied on a transitive HTTP dependency; we made it a direct dependency.
- The repository initially lacked required continuous-integration checks; we added them.
- The latest published MCP conformance runner did not include the final protocol revision used
  by the deployed target.
- The older full conformance suite assumed a reference server supporting optional capabilities,
  so many failures were fixture mismatches rather than protocol failures.
- Direct local FastMCP HTTP did not provide the same Host and Origin boundary as Horizon. Local
  HTTP is therefore documented as loopback-only.

These should not be presented as Horizon defects.

### Expected behavior, not defects

- A separate email verification step during first sign-in was normal identity assurance.
- Tool Permissions showing the production manifest was consistent with its production policy
  role, even though a preview view would be useful.
- Rollback creating a new deployment is a sound immutable-release model.
- Optional request and response logging is a necessary privacy decision, not missing
  observability.
- A cold start is a normal consequence of scaling idle compute to zero.

## Current launch status

The server is suitable for an **authenticated organization beta**:

- the endpoint is internet-addressable but does not allow anonymous use;
- production exposes one read-only diagnostic tool;
- remote targets must match an operator-owned HTTPS allowlist;
- caller credentials and arbitrary headers cannot be forwarded;
- time, concurrency, response size, catalog size, schema depth, and returned data are bounded;
- approved and denied requests were tested in production;
- request and response payload logging is disabled;
- rollback and restoration were exercised successfully;
- the local nine-tool MCP Doctor server and its test suite remain intact.

It should not yet be described as an anonymous or unrestricted public service. Before broader
access, we recommend:

1. running a final conformance suite for the negotiated MCP protocol revision when one is
   published;
2. confirming documented per-user rate, concurrency, and audit-retention behavior;
3. defining membership and tool roles narrower than the current organization-wide Admin
   default;
4. testing realistic multi-user load and abuse cases;
5. establishing a searchable application-to-gateway correlation mechanism.

## Recommendation

Horizon is a strong fit for prototypes, personal servers, interviews, and authenticated team
betas. Its managed identity, gateway, deployment, audit, and recovery capabilities save
meaningful engineering work and reduce the likelihood of serious security mistakes.

For larger production adoption, the highest-priority investment should be the safe-release
workflow: revision-aware entrypoint configuration, deterministic preview registration, explicit
configuration state, and an automation interface with the same capabilities as the dashboard.

The product does not need a different value proposition. It needs the existing value
proposition to behave more predictably at the boundary between a pull request and production.

## Concise interview narrative

> Horizon delivered the difficult production boundary—identity, gateway security, deployment,
> observability, and rollback—while MCP Doctor retained responsibility for outbound and
> application safety. The deployment succeeded and the value proposition was validated. The
> exercise also revealed maturity gaps in preview configuration and automation, especially
> when a pull request introduces a new server entrypoint. We compensated with a fail-closed
> application design, exact destination allowlisting, bounded execution, privacy-preserving
> logging, and a tested rollback path.
