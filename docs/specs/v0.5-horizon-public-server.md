# MCP Doctor v0.5 plan: public Horizon server

Status: proposed for implementation.
Scope: roadmap steps 1 through 5: baseline, probe deploy, friction capture,
hosted-safe surface, and an end-to-end public beta demonstration.
Target: an internet-addressable MCP Doctor endpoint deployed on Prefect Horizon.

## 1. Outcome and release posture

MCP Doctor v0.5a will be a useful public MCP server, not a remote wrapper around the
trusted local v0.4 process.

For this plan, **public** means internet-addressable and available for users to connect
to through standard MCP clients. It does not mean anonymous. Every production request
must be authenticated, attributed to a principal, authorized for the requested tool,
rate limited, and auditable.

The first hosted release exposes one coherent capability: inspect and deterministically
diagnose an allowlisted or otherwise egress-safe remote HTTPS MCP server. It does not:

- accept local file paths, MCP configuration files, or executable targets;
- start Python, JavaScript, or shell processes;
- accept bearer tokens, API keys, or arbitrary HTTP headers in tool arguments;
- make model calls or expose billable eval execution;
- write caller-selected paths or promise durable report storage;
- expose Lab orchestration tools.

Those exclusions are release boundaries, not abandoned features. They keep the first
public surface useful while preventing the local v0.4 trust assumptions from crossing
an internet boundary accidentally. Hosted evals and durable artifacts follow after the
remote identity, target-auth, storage, and background-task contracts are designed.

## 2. Evidence and standards baseline

Implementation must be checked against the current dated MCP specification and the
versions actually resolved in the repository, rather than undated examples.

At plan creation, the repository resolves FastMCP 4.0.5 and fastmcp-tasks 4.0.5, and
declares `fastmcp[tasks]>=4.0,<5`. Before implementation, record the resolved versions
and confirm which dated protocol revisions Horizon and the intended clients negotiate.

Relevant primary guidance:

- [MCP 2026-07-28 security best practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)
  cover token passthrough, SSRF, redirects, DNS rebinding, state-handle ownership, and
  least-privilege scopes.
- [MCP 2026-07-28 authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
  requires audience-bound tokens, protected-resource metadata, correct 401/403 behavior,
  and authorization on every HTTP request.
- [Horizon Deploy](https://www.prefect.io/horizon/deploy) describes Git-based builds,
  OAuth, preview deployments, scaling, monitoring, and background-task support. Every
  claim needed by this plan must still be verified in the deployed project.
- [MCP conformance](https://github.com/modelcontextprotocol/conformance) provides frozen
  requirement sets for dated protocol revisions. Run the server requirements applicable
  to the deployed endpoint instead of treating an SDK dependency as proof of conformance.

Tool annotations are useful client hints, but they are not authorization or sandboxing.
Enforcement belongs in Horizon policy, the hosted tool contract, target validation,
resource limits, and network controls.

## 3. Target architecture

```text
MCP client
    |
    | OAuth-authenticated Streamable HTTP
    v
Horizon gateway
    - identity and token validation
    - tool-level authorization
    - rate/concurrency policy
    - request and decision audit
    |
    | verified principal and authorized tool call
    v
MCP Doctor hosted server
    - hosted-only allowlisted tool registry
    - strict input models and public error mapping
    - target policy and resource budgets
    - no local process or arbitrary filesystem access
    |
    | controlled HTTPS egress
    v
egress enforcement / target validator
    - DNS and IP policy
    - redirect revalidation
    - private/reserved network denial
    - response and time limits
    |
    v
permitted remote MCP endpoint
```

The local STDIO entrypoint remains a separate deployment surface. It keeps the nine v0.4
tools and trusted-local workflows. Horizon must point to a new hosted entrypoint, not to
`mcp_doctor.server:mcp`.

Prefer a separate module such as `mcp_doctor.hosted_server:mcp` over a boolean mode on the
existing factory. An explicit hosted allowlist fails closed: adding a local tool later
cannot expose it remotely merely because somebody forgot a mode check.

## 4. Security invariants

The following are release gates, not aspirational follow-ups.

1. Production is authenticated by default. An unauthenticated MCP request fails before
   application tool execution.
2. The hosted module registers only explicitly reviewed hosted tools. It never imports a
   function that registers all local tools as a side effect.
3. Hosted inputs cannot name local files, output paths, commands, environment variables,
   HTTP headers, or raw credentials.
4. The first public tool performs MCP discovery and listing only. It never invokes a
   target tool.
5. Production targets use HTTPS. The beta either uses an explicit target allowlist or a
   network control that blocks private, loopback, link-local, multicast, reserved, and
   cloud metadata destinations for IPv4 and IPv6.
6. The same target policy applies to the initial URL, DNS answers, every redirect, and
   every OAuth or protected-resource discovery URL. Application checks alone are not
   sufficient protection against DNS rebinding.
7. Target tokens are never accepted from users and never passed through. A future
   authenticated-target feature must use audience-specific service credentials or a
   delegated authorization design.
8. Every request has finite time, response-size, component-count, schema-size, nesting,
   concurrency, and rate budgets. Limit failures are explicit and non-retryable by
   default.
9. Public responses and errors do not expose filesystem paths, environment data, stack
   traces, resolved internal addresses, credentials, or raw downstream bodies.
10. Target-provided names, descriptions, schemas, and errors are untrusted data. They are
    bounded and normalized before inclusion in a tool result or log.
11. Audit records identify the principal, deployment revision, tool, policy decision,
    target origin, timing, outcome category, and correlation ID without logging secrets.
12. A deployment is not publicized until rollback is exercised and the previous known-good
    revision can be restored.

## 5. Threat model for the first public tool

| Threat | Why it matters | Required control | Release evidence |
| --- | --- | --- | --- |
| Anonymous abuse | Diagnosis causes outbound traffic and computation. | Horizon auth required; no anonymous production mode. | Unauthenticated discovery and call attempts fail. |
| Cross-user privilege | A user may reach tools or state belonging to another role. | Least-privilege tool policy; no shared caller state in v0.5a. | Restricted principal cannot discover or invoke a denied tool. |
| SSRF and network scanning | Caller supplies the remote target URL. | HTTPS, target allowlist or hardened egress, IP/DNS/redirect checks, one target per call. | Tests cover private IPv4/IPv6, metadata, redirects, and rebinding strategy. |
| Token passthrough | A public proxy could forward credentials to the wrong audience. | No credential/header inputs; unauthenticated targets only in v0.5a. | Schemas contain no secret-bearing fields and audit contains no tokens. |
| Local code execution | v0.4 accepts local scripts and configs that may launch processes. | Hosted module has no local target/config fields and no subprocess path. | Hosted tool schema and negative tests prove absence. |
| Arbitrary file access | v0.4 comparison and artifact tools accept absolute paths. | No path-bearing hosted tools and no caller-selected saves. | Hosted catalog contains no path parameters. |
| Resource exhaustion | Malicious servers can return huge catalogs, schemas, or slow streams. | End-to-end deadline, byte/count/depth budgets, bounded concurrency, cancellation. | Oversize, slow, deep-schema, and disconnect tests fail predictably. |
| Prompt/tool-definition injection | Target descriptions are later shown to an agent. | Treat downstream text as data, cap strings, omit raw instructions from compact results. | Malicious-description fixture cannot alter result structure or server behavior. |
| Information leakage | Detailed errors and audit payloads can expose internals. | Stable public error taxonomy, masked internals, reviewed audit retention/redaction. | Error snapshots contain no paths, stack traces, or secret values. |
| Dependency or build drift | Horizon rebuilds may resolve a different SDK version. | Frozen lock or exact deploy constraints; record build SHA and dependency versions. | Rebuild of the same revision has the same dependency inventory. |
| Replay/duplicate calls | Clients and networks may retry idempotent operations. | Hosted diagnosis is read-only and idempotent; correlation IDs distinguish attempts. | Repeated calls produce equivalent analysis without persistent side effects. |

## 6. Hosted tool contract

The initial hosted server should expose one tool with an unambiguous name, for example
`diagnose_remote_mcp_server`.

Suggested conceptual input:

```json
{
  "target_url": "https://example.com/mcp",
  "policy_profile": "default",
  "timeout_seconds": 20
}
```

Contract requirements:

- `target_url` is a single production HTTPS MCP URL. Public beta rejects userinfo,
  fragments, IP-literal hosts, non-approved ports, and URLs above the documented length
  limit. Any compatibility exceptions must be explicit server configuration, not caller
  switches.
- `policy_profile` selects a server-owned, versioned policy such as `default` or `strict`.
  It never refers to a path and cannot upload arbitrary policy contents.
- `timeout_seconds` has a conservative server default and a low hard maximum. The overall
  operation deadline includes connection, protocol negotiation, listings, and analysis.
- The operation lists tools, resources, resource templates, and prompts but never calls
  a target tool.
- The response is a bounded structured summary: target origin, negotiated protocol and
  server identity, inventory counts, deterministic metrics, capped findings, omitted
  counts, policy/analysis versions, outcome category, and correlation ID.
- No full report is persisted in v0.5a. The response must not claim a durable artifact.
- An auth challenge from the target returns a specific `target_auth_required` outcome.
  The hosted server must not launch an interactive browser flow.

Suggested public error categories:

- `invalid_target`
- `target_not_permitted`
- `target_auth_required`
- `target_unreachable`
- `target_timeout`
- `target_too_large`
- `target_protocol_error`
- `request_rate_limited`
- `service_unavailable`
- `internal_error`

Expected errors should give a safe action the caller can take. Unexpected errors should
return only a correlation ID while retaining diagnostic detail in operator-only logs.

Tool annotations should say the operation is read-only, idempotent, non-destructive, and
open-world. Tests must not treat those annotations as enforcement.

5. Decide whether the pushed v0.4 branch will be merged before deployment or used through

## 8. Step 2: private, unchanged Horizon probe

The probe deliberately deploys the current local server entrypoint before hosted changes.
It is private to the project owner and is never advertised as the public server. Its job
is to expose build, platform, and client friction with minimal confounding changes.

### Horizon setup

1. Create a preview project from the recorded Git revision.
2. Use `src/mcp_doctor/server.py:mcp` as the probe entrypoint.
3. Use repository dependency metadata and record whether the lockfile is honored.
4. Require Horizon authentication and restrict project access to the owner.
5. Do not add production secrets. `OPENAI_API_KEY` is unnecessary for diagnosis and should
   remain absent during the probe.
6. Capture the generated endpoint, deployment ID, build ID, region, runtime, and visible
   configuration without committing credentials or private URLs.

### Probe matrix

| Area | Test | Expected observation |
| --- | --- | --- |
| Build | Deploy clean revision. | Build either succeeds reproducibly or produces actionable dependency/entrypoint evidence. |
| Auth | Request discovery without credentials. | Request is rejected before tool execution and an auth event is visible. |
| OAuth | Connect from the intended MCP client. | Browser flow completes and the client reconnects without copying a token. |
| Discovery | List tools as the owner. | Nine local tools appear, proving why a separate hosted catalog is required. |
| Safe call | Diagnose a known public HTTPS MCP endpoint without `save_path`. | Compact result returns and no target tool is called. |
| Audit | Inspect the corresponding Horizon event. | Principal, tool, status, timing, deployment, and request identity are present. |
| Error | Diagnose an invalid or unreachable test hostname. | Client receives a bounded error and operators retain enough detail to debug. |
| Cold start | Let the service scale down, then repeat discovery and diagnosis. | Behavior is correct; latency and any transient error are recorded. |
| Rollback | Promote or restore the prior build. | Endpoint returns to the known revision and audit shows the lifecycle event. |

Do not invoke path-bearing tools or submit local paths during this probe. Their discovery
is sufficient evidence that the v0.4 surface is not the public contract.

### Exit criteria

- We know the exact Horizon build and entrypoint contract.
- OAuth works with at least one intended MCP client.
- We have one successful authenticated diagnosis and its audit event.
- Every unexpected behavior is recorded before a workaround is applied.
- Rollback has been exercised once.

## 9. Step 3: capture and triage friction

Use `docs/v0.5-horizon-friction-log.md` as the append-only human record for the spike.
Do not overwrite a failed attempt after finding a workaround.

Each entry records:

- timestamp, actor, Git SHA, deployment/build ID, client, and protocol revision;
- stage and exact user goal;
- expected and actual behavior;
- sanitized error or log reference;
- time spent and number of manual steps;
- workaround, if any;
- owner: Doctor, Horizon, FastMCP, MCP client, documentation, or unknown;
- severity: observation, paper cut, workaround required, or blocker;
- whether it affects security, usability, reliability, cost, or interview narrative;
- proposed product or documentation change and verification status.

Triage after the probe into four queues:

1. **Must fix before public:** auth bypass, SSRF, secret exposure, unsafe tool discovery,
   arbitrary path/process access, missing limits, or unreliable rollback.
2. **Must fix before demo:** client incompatibility, confusing OAuth, non-actionable build
   failure, or inability to produce and find an audit event.
3. **Can document for beta:** bounded limitations with safe workarounds.
4. **Platform question:** behavior that requires confirmation from Horizon rather than an
   application workaround.

The log is an engineering artifact, not a complaint list. Each high-severity entry must
end with an owner, next experiment, or explicit release block.

## 10. Step 4: implement the hosted-safe surface

### 10.1 Separate entrypoint and dependency direction

Add a dedicated hosted module that constructs its own `FastMCP` instance and registers
only reviewed remote-safe tools. Reuse pure inspection, analysis, policy, and presentation
functions; do not reuse the v0.4 registration function.

Suggested files:

```text
src/mcp_doctor/
    server.py                 trusted local nine-tool server, unchanged contract
    hosted_server.py          Horizon entrypoint and hosted tool registration
    hosted_settings.py        strict environment-derived operator settings
    target_security.py        target policy abstraction and safe errors
tests/
    test_hosted_server.py
    test_target_security.py
    test_hosted_limits.py
docs/
    hosted.md                 operator and client runbook
```

`hosted_settings.py` must fail fast on invalid production configuration. Do not silently
fall back from an absent allowlist/egress policy to unrestricted network access.

### 10.2 Target and egress policy

Define a `TargetPolicy` abstraction so application validation and platform/network
enforcement can be tested independently. Do not scatter URL checks through workflows.

The beta policy should:

- accept a single parsed HTTPS URL;
- reject embedded credentials, fragments, IP literals, and disallowed ports;
- normalize the origin for audit without logging query secrets;
- resolve A and AAAA records and reject any non-global answer;
- apply the same rules to every redirect and discovered authorization URL;
- disable redirects unless needed, otherwise use a small hard redirect limit;
- use a network-layer egress restriction or proxy to defeat DNS rebinding and TOCTOU;
- fall back to a server-owned hostname allowlist if Horizon cannot provide safe general
  egress for the public beta;
- reject targets that require interactive authorization in v0.5a.

Do not write a bespoke alternative to the platform HTTP stack merely to add IP checks.
First determine where FastMCP exposes transport configuration and where Horizon can
enforce outbound policy. If neither gives a sound control, keep the beta allowlisted.

### 10.3 Resource budgets

Introduce explicit hosted inspection limits and enforce them as early as the transport
allows:

- overall operation deadline and per-request timeout;
- maximum redirect count;
- maximum response body and aggregate catalog bytes;
- maximum components per list operation;
- maximum serialized bytes per component/schema;
- maximum JSON/schema nesting depth;
- maximum string length retained in results and logs;
- per-principal rate and concurrency limits;
- global concurrency/backpressure limit.

Choose initial numeric thresholds from the probe and a small corpus of legitimate public
servers. Store them as reviewed configuration with safe defaults and absolute ceilings.
No limit may be disabled by a normal tool argument.

Cancellation must release connections and analysis work. A timeout must not leave a
background coroutine or target connection running.

### 10.4 Authentication and authorization

Horizon owns the external OAuth flow. Verify, rather than assume, that it provides:

- protected-resource metadata and standards-compliant 401 challenges;
- audience and issuer validation;
- a usable flow for the chosen desktop/CLI clients;
- tool-level access policy and discovery filtering;
- identity and policy-decision context in audit events;
- service-account support for future automation.

Define a minimal initial permission such as `doctor:inspect`. Do not request eval, admin,
or write scopes for the first public tool. If verified identity or scopes reach the
application, add FastMCP authorization checks as defense in depth. If Horizon terminates
authorization without forwarding claims, document that trust boundary explicitly.

Correct error behavior is part of acceptance: missing/invalid credentials produce 401,
while an authenticated principal lacking permission produces 403.

### 10.5 Output, errors, logs, and privacy

Keep `mask_error_details=True`, then add a hosted-specific mapping from internal exceptions
to the public error categories in this document. Expected target failures must not become
generic internal errors, and unexpected exceptions must not be reflected verbatim.

The hosted result must:

- cap every variable-length collection and include omitted counts;
- omit raw target instructions and full component descriptions by default;
- remove control characters from retained target text;
- identify target-supplied data as untrusted;
- include analysis and policy versions;
- include a correlation ID safe to show the caller;
- avoid local paths and deployment internals.

Determine exactly what Horizon stores from arguments, results, errors, and headers. Set a
documented retention/redaction policy before launch. The public tool schema itself must
make secret submission unnecessary; warnings such as “do not paste tokens” are not a
substitute for removing secret-shaped fields.

### 10.6 Tool quality and self-diagnosis

The hosted tool should have:

- a specific name and concise positive/negative selection guidance;
- strict Pydantic inputs with `extra="forbid"`;
- accurate output schema where supported;
- explicit read-only, non-destructive, idempotent, and open-world annotations;
- no hidden optional fields that expand authority;
- a compact result suitable for another agent to reason over.

Run MCP Doctor's own deterministic analysis against the hosted server and require zero
active warnings. Compare the hosted surface with the local surface as peers to document
the intentional reduction; do not call the missing local tools regressions.

### 10.7 Tests and CI

Add tests at four levels.

**Unit**

- strict hosted input validation and absence of path/header/credential fields;
- public error mapping and sanitization;
- limit accounting and omitted counts;
- settings fail closed;
- annotations and tool description accuracy.

**Adversarial integration fixtures**

- private, loopback, link-local, IPv4-mapped IPv6, and metadata destinations;
- mixed safe/unsafe DNS answers and redirect-to-private behavior;
- slow response, disconnect, invalid JSON-RPC, oversized body, huge tool list, deeply
  nested schema, very long strings, and malicious instructions in descriptions;
- target 401/auth discovery behavior without browser launch;
- cancellation and repeated calls.

**MCP integration**

- hosted catalog contains exactly the reviewed tools;
- diagnosis never calls a target tool;
- local server still exposes its existing nine tools;
- current v0.4 tests and artifact formats remain compatible.

**Deployed checks**

- unauthenticated 401, unauthorized 403, authenticated discovery/call;
- current dated MCP server conformance requirement set;
- Horizon audit correlation;
- cold start, modest concurrent load, timeout, and rollback.

### Exit criteria

- The hosted entrypoint cannot reach local/process/path code through its tool schema.
- General egress is network-enforced, or the beta is restricted to an explicit allowlist.
- All security and compatibility tests pass.
- Local STDIO behavior remains unchanged.
- The hosted surface diagnoses itself with no active warnings.
- Documentation states the exact public capabilities and limitations.

## 11. Step 5: deploy and prove the golden path

### 11.1 Preview deployment

1. Deploy `src/mcp_doctor/hosted_server.py:mcp` from a pull-request preview.
2. Confirm the build uses the intended lock/constraints and record installed versions.
3. Require authentication and grant only the minimal inspection permission.
4. Configure the reviewed target allowlist or verified egress policy.
5. Configure conservative per-principal rate/concurrency limits and global backpressure.
6. Use no OpenAI key, database credential, or downstream bearer token.

### 11.2 Demo target

Use a deterministic, non-sensitive HTTPS MCP target. There are two acceptable options:

- an existing public documentation/test MCP endpoint included in the target policy; or
- a separately deployed, clearly labeled demo-only instance of `examples/eval_server.py`
  with no secrets or durable state and its own abuse controls.

Do not weaken the Doctor's egress policy merely to make the demo target convenient. If
the demo target is Horizon-authenticated, service-to-service authorization becomes a
separate required design; do not paste its user token into a Doctor tool call.

### 11.3 Golden-path script

1. Connect a fresh MCP client to the public Doctor URL.
2. Complete Horizon OAuth without copying a token manually.
3. List the hosted tools and show only the reviewed public surface.
4. Call `diagnose_remote_mcp_server` for the approved target.
5. Show the bounded structured result and explain that no target tool ran.
6. Locate the Horizon audit event using the correlation ID.
7. Show principal, tool, policy decision, deployment revision, duration, and outcome.
8. Attempt one prohibited action: unauthenticated access, denied principal, or blocked
   target. Show the safe client error and corresponding audit decision.
9. Repeat after a cold start.
10. Roll back once to the previous known-good deployment and confirm service recovery.

### 11.4 Public launch gate

The URL can be described as a public beta only when all of the following are true:

- Auth is mandatory and works in the supported client matrix.
- The hosted catalog contains no local/path/process tools.
- SSRF protection is enforced at the network layer or targets are allowlisted.
- Rate, concurrency, time, and size limits are active and tested.
- Errors and audit records have been reviewed for secret/internal leakage.
- The dated MCP conformance run has no unexplained required failures.
- Dependency/build provenance and rollback are recorded.
- The friction log contains no unresolved public-release blocker.
- README and hosted runbook accurately state that v0.5a is remote diagnosis only.

## 12. Implementation slices

Keep review units small enough that each security boundary can be evaluated independently.

1. **Plan and baseline:** this spec, friction-log template, baseline evidence, and no
   runtime behavior change.
2. **Hosted catalog:** separate entrypoint, one strict tool, no paths/processes, unit and
   MCP integration tests.
3. **Target security and limits:** policy abstraction, safe egress integration or explicit
   allowlist, budgets, adversarial fixtures, and error taxonomy.
4. **Horizon preview:** deployment configuration, auth/policy/audit tests, conformance,
   cold-start and rollback evidence.
5. **Public beta documentation:** client setup, supported behavior, limits, privacy,
   operator response, and known safe limitations.

Do not combine hosted evals, durable artifact storage, Redis/Docket, Prefect flows, or
scheduling into these slices. Evidence from this work should determine those designs.

## 13. Decisions the probe must answer

1. Does Horizon build from `uv.lock`, or does it independently resolve project ranges?
2. Which MCP revisions do the deployed FastMCP server, Horizon gateway, and intended
   clients actually negotiate?
3. Can Horizon enforce outbound destination policy, or must the beta use a hostname
   allowlist/external egress proxy?
4. Can Horizon rate-limit and cap concurrency per principal and per tool?
5. Does tool-level policy also filter `tools/list`, or only reject invocation?
6. Which identity/role/scope claims, if any, are forwarded to application code?
7. What portions of MCP arguments, structured results, errors, and headers are retained
   in audit logs, for how long, and with what redaction controls?
8. Are preview secrets isolated from production, and can preview deployments be prevented
   from receiving production credentials?
9. Does Horizon expose deployment/build identity to the application or audit event?
10. What is the supported rollback mechanism and expected recovery behavior?

An unknown answer is acceptable during the private probe. It is not acceptable at the
public launch gate if it affects a security invariant.

## 14. Definition of done for steps 1 through 5

Steps 1 through 5 are complete when a new authenticated user can connect to the Horizon
URL with a supported MCP client, discover only the hosted-safe tool, diagnose an approved
remote HTTPS MCP endpoint, receive a bounded deterministic result, and correlate it with
an identity-aware audit event. A denied request must fail safely and be auditable. The
same path must survive a cold start, and operators must have exercised rollback.

Completion also requires preservation of the local nine-tool server and its existing test
suite. A successful Horizon build by itself does not satisfy this definition.

Deployment status on 2026-09-22: the implementation, isolated preview, authenticated
production path, safe denied request, cold connection, audit inspection, and
rollback/restoration are verified. The deployed endpoint is an organization-authenticated
beta. General-audience qualification remains gated on a final 2026-07-28 conformance suite
and documented per-principal abuse controls that the current Horizon plan does not expose.
